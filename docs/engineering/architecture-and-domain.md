# Architecture and domain conventions — history and measurements

This file is the record behind `CLAUDE.md` "Architecture and patterns" and "Domain conventions": the measurements behind rules whose paragraphs were trimmed to the rule.

Each section is the `CLAUDE.md` text as it stood when it moved here (#2860), so its present tense describes that moment. Read `CLAUDE.md` and the code for what is true now.

## Moved in the second audit pass

**Shared script registration is not the orchestrator's either** (#1924). `Core\AssetRegistry` registers `ffc-core` (with `ffcCoreConfig`), the field behaviours, the front-end helpers (`ffc-rate-limit`), the captcha and the dynamic fragments, on the front end and at priority 1 of every admin request; `Loader` only calls its `init()`. It moved because it had measurably drifted: on an FFC admin screen `ffcCoreConfig` was localized twice, once by `Loader` and once by `AdminAssetsManager`. **Every script more than one site enqueues lives in its `SCRIPTS` map too** (#1931) — path and dependencies, once — and a site names it with `AssetRegistry::enqueue_scripts( 'handle' )`, which registers the handle and the shared scripts it depends on before enqueuing, so it works before the registration hook has fired. The sites had restated the source at every call and WordPress kept whichever registered first: `ffc-pdf-generator` had two dependency lists and two paths, and two literal paths served the readable source in production. A dependency only one screen needs (the form editor's field builder ahead of `ffc-admin-js`) is enqueued first by that screen, never added to the map. **Shared stylesheets follow the same rule** through `AssetRegistry::enqueue_styles( 'handle' )`, whose cases are literal `wp_enqueue_style()` calls rather than a map, because the stylesheet guards read the dependency graph off those calls. The palette stays `AssetHelper::enqueue_common_style()`, its single declaration, which the caller enqueues first. Four sheets shared a handle with a script of the same name and took a `-css` suffix (`ffc-audience-css`, `ffc-working-hours-css`, `ffc-custom-fields-admin-css`, `ffc-url-shortener-admin-css`): scripts and styles live in separate registries, so the clash broke nothing, but one name for two files cost a lookup at every site.

A form's settings (`_ffc_form_config`, `_ffc_form_fields`, the background) are read with `get_post_meta()`, through `FormRepository::getConfig()` / `getFields()` where a repository is in hand. **Do not put a plugin cache in front of them.** WordPress already caches post meta for the request and, with a persistent object cache, across requests, so a second copy saves no query and adds an invalidation duty: `FormCache` existed for that and lost. When #2241 measured it, two readers used it (the REST controllers and bulk issue), every main path read the meta directly, its Enable setting gated nothing, and three call sites had to clear it by hand after writing the meta. It went through a deprecation cycle in 6.43.0 with its warming job and its three settings, and left in 6.45.0 (#2552). What stays in `FormCache` is the page-cache purge (`purge_page_cache()`, `purge_external_caches()`, `purge_all_pages()`), which is a different job: telling third-party page caches that the page embedding a form changed. The class keeps its name because a rename would ride every call site for nothing; the name is the known lie, recorded here.

**ALTCHA specifics that are not guessable and cost time to rediscover** (all verified against the vendored bundle, not documentation — 3.2.2 first, re-run against 3.3.0 in #1604, against 3.4.0 in #1928 and against 3.6.0 in #2643):

- **The wire format is the widget's own ("v2") challenge, and a v1 payload is refused** (#1928). `create_challenge()` returns `{parameters: {algorithm, cost, expiresAt, keyLength, keyPrefix, nonce, salt}, signature}`; the solver derives `SHA-256(salt || nonce || uint32_be(counter))` until the key starts with `keyPrefix` and posts back `{challenge: {parameters, signature}, solution: {counter, derivedKey, time}}` in base64. The challenge is deterministic — the server draws the counter and publishes half the key it derives — and the signature covers every parameter, the expiry included, so the salt/number split of CVE-2025-68113 (#1357) has no boundary to move. The plugin spoke the original v1 shape until 3.4.0 broke the widget's conversion shim (`isChallengeV1()` compares the challenge with the string `"object"`), which made every v1 challenge fail with "Challenge validation failed" (reported upstream as altcha-org/altcha#202): **a format the widget only reads through a shim is one upstream refactor away from breaking, so speak the native one.** `tests/Support/AltchaSolver.php` solves challenges the widget's way for the tests; the end-to-end check is the real widget in Chromium against the real PHP.

On/off **toggle switches** (`.ffc-control-toggle`, rendered via `AdminUI::render_toggle()`) auto-save on flip: mark the input `data-ffc-autosave-key="<key>"`, add the key to `SettingsAjaxEndpoint::allowlist()` (`{option, path?, type, cap}`), and have the tab call `enqueue_autosave_infra()`. This is the standard for atomic, side-effect-free boolean settings. **Two autosave endpoints exist and stay separate on purpose** (do NOT unify — bad-façade trap): `SettingsAjaxEndpoint` (`ffc_update_setting`) writes WP **options** under a global cap; `FormMetaAjaxEndpoint` (`ffc_update_form_meta`, attribute `data-ffc-autosave-form-key`) writes per-post **meta** gated on `edit_post` of that exact form. **The JS is one widget serving both** (#1116) — `FFC.Admin.autoSaveField` in `assets/js/ffc-admin-autosave.js`, wired by `bootAutoSaveFields()`, which scans **both** attributes and takes `action` / `payload` / `request` / `strings` per endpoint. The endpoints stay separate; only their client did not need to be. That statement was written here before it was true: the form-meta half was a second implementation inside `assets/js/ffc-admin.js` (delegated, `change` only, no debounce, its own badge whose CSS hardcoded hex and therefore ignored dark mode), and the cost was not theoretical — the #1114 validity guard had to be written twice to reach both halves. So a change to autosave behaviour is now one edit; **a screen that renders either attribute must enqueue `ffc-admin-autosave`** (settings tabs get it from `enqueue_autosave_infra()`, the form editor enqueues it directly), or its fields silently have no listener.

Two things the convergence measured, worth not re-deriving. Every one of the 16 form-meta fields is a checkbox from `AdminUI::render_toggle()`, so adopting the settings half's `change`+`input` binding changed nothing visible — there is no text field on that path to "save while typing", and a checkbox's two events coalesce in the debounce. And the **delegated** binding was the half *not* kept, against the original proposal: nothing exercises it (all fields of both kinds are server-rendered at page load), and adopting it would have meant rewriting the half with 115 fields, per-field debounce, multi-checkbox groups and `confirmOff` to gain that. `bootAutoSaveFields()` is idempotent and exported, so DOM inserted later has a supported answer — call it again.

- **Never log raw PII.** Debug logs hash IPs / CPF — a truncated **keyed** hash, never the value — and stay behind the off-by-default debug toggles regardless. See `IpGeolocation` and `ClientIpResolver` (16 hex chars of `Encryption::keyed_hash()`) and `PreflightTelemetry` (12 of `IpAddress::fingerprint()`) (#596, #2109). A bare `hash( 'sha256', $ip )` is not a hash here: the IPv4 space is 2^32 addresses, so a table reverses it, which is what those two call sites shipped until #2109. **The truncation length is the call site's, not a plugin-wide constant**; this file used to quote one length for all of them and disagreed with `PreflightTelemetry` for as long as it did. What is plugin-wide is the rule: hash before logging.
